# Process registry workbench

A test bench for distributed process registries on the BEAM. It starts a
three node Erlang cluster in docker, cuts and heals the network between the
nodes with iptables, and records what each registry answers while that
happens.

The registries under evaluation:

| Registry | What it is |
| --- | --- |
| [`global`](https://www.erlang.org/doc/apps/kernel/global.html) | OTP's own name registry, in kernel |
| [`gproc`](https://github.com/uwiger/gproc) | global scope, leader elected with `gen_leader` |
| [`syn`](https://github.com/ostinelli/syn) | full replication, gossip between nodes |
| [`horde`](https://github.com/derekkraan/horde) | full replication over a delta CRDT, membership follows the visible nodes |
| [`group`](https://github.com/phoenixframework/group) | sharded replicas, async replication over Erlang distribution |
| [`locker`](https://github.com/wooga/locker) | quorum writes with leases, from Wooga |
| [`highlander_pg`](https://hex.pm/packages/highlander_pg) | a Postgres advisory lock, not on the BEAM at all |

`horde`, `group` and `highlander_pg` are Elixir libraries, so the image
carries Elixir as well as Erlang (see [`elixir/mix.exs`](elixir/mix.exs)).

`group` is the registry underneath Chris McCord's DurableServer, usable on
its own. DurableServer itself is not evaluated here: it adds durable state
in object storage, which is a different concern from finding a process.

`highlander_pg` is the odd one out and worth reading about before the
numbers, because it inverts the usual arrangement: rather than registering
a process you already have, you hand it a child spec, every node polls `pg_try_advisory_lock`, and whoever wins
starts the process. Two things follow. A claim is not a decision, so
`claim/1` answers `pending` and the workbench waits up to `CLAIM_SETTLE_MS`
for the lock to land. And there is no cluster wide lookup: a node can only
answer for itself, so a healthy cluster has one node reporting a pid and
the rest reporting nothing, which the agreement column reads as
disagreement. For this registry the owner count is the column that means
something.

## Can they all be used as `{via, Module, Name}`?

Not all, and the exceptions say something:

| Registry | `{via, ...}` |
| --- | --- |
| `global` | yes, natively |
| `gproc` | yes, `{via, gproc, {n, g, Key}}` |
| `syn` | yes, natively |
| `horde` | yes, `{via, Horde.Registry, {Name, Key}}` |
| `group` | no via module, and `register/4` registers the caller, so the claim has to be made from inside the process |
| `locker` | yes, through [`locker_via`](src/locker_via.erl) in this repo, with two losses: the yes/no protocol hides whether a refusal was a taken name or a missing quorum, and locker never frees a name on its own |
| `highlander_pg` | no. Via registration happens inside the starting process; HighlanderPG decides whether to start it at all |

That last row is why the adapter callback is `claim/1` (make a process own
this name) rather than a via shaped `register_name/2`: the via protocol
cannot express a registry that owns process creation.

Because locker does not free a name when its owner dies, the registered
process gives it back itself in `workbench_worker:terminate/2`, driven by
the `frees_name_on_exit/0` property of the adapter. That covers an orderly
stop. It cannot cover a crash: `exit(Pid, kill)` never runs `terminate/2`,
which is what the process death scenario shows.

The output is [`results/RESULTS.md`](results/RESULTS.md), generated by the run.

## What the run found

From the run recorded in [`results/RESULTS.md`](results/RESULTS.md): OTP 27,
one run per registry, 8 scenarios, 29 cluster wide lookups each.

| | `global` | `gproc` | `syn` | `horde` | `group` | `locker` | `highlander_pg` |
| --- | --- | --- | --- | --- | --- | --- | --- |
| Two owners at once during a partition | yes | yes | yes | yes | yes | **no** | **no** |
| Owners during a three way split | 3 | 3 | 3 | 3 | 3 | **1** | **1** |
| Frees the name when the process dies | yes | yes | yes | yes | yes | no, at lease expiry | yes |
| Leases | no | no | no | no | no | yes | no |
| Lookups where the nodes disagreed | 8/29 | 11/29 | 8/29 | 19/29 | 17/29 | **0/29** | 27/29, by design |
| Slowest single action | 9ms | 5012ms | 7ms | **9ms** | 13ms | 7012ms | 3102ms |
| Claims refused | 3 | 3 | 3 | **0** | 3 | 8 | 0 |

* **`global`, `gproc` and `syn` behave alike.** Lookups are local and answer
  in single digit milliseconds, and every partition scenario ends with two
  processes owning the same name, three in the full split. All three
  converge on one owner after the network heals.
* **Who survives the heal differs.** With the owner isolated on n3 and the
  majority claiming the name on n1, `global` and `syn` kept the majority's
  process; `gproc`, `horde` and `group` kept n3's and discarded the
  majority's.
* **`horde` never refuses anything.** It is the only registry that accepted
  every claim: registration is a local CRDT write, so a second node
  claiming a name that is already taken succeeds, and the duplicate is
  resolved later by killing one of the two with
  `{name_conflict, ...}`. That happened on a *healthy* cluster in the
  baseline scenario, because the workbench claims twice within
  milliseconds and the CRDT had not propagated yet. It is also the only
  registry that never blocked: its slowest action anywhere was 9ms,
  partition or not. Most of its 19 disagreements are that same propagation
  lag, and after a 15 second settle the nodes agree.
* **`group` splits the difference.** Writes are authoritative and reads are
  not: a registration is routed to the shard that owns the key, so the
  duplicate claim in the baseline was refused with `taken` where Horde
  accepted it, but the result is replicated to the other nodes
  asynchronously, so a lookup in the same millisecond still misses. That is
  where its 17 disagreements come from; a moment later the nodes agree. It
  never blocked either, 13ms at worst, and it split-brained under partition
  like the other CRDT and gossip based ones.
* **`gproc` did not recover from the three way split.** In the scenario
  that ran next, a registration on n2 died with a
  `{timeout, {gen_leader, leader_call, ...}}` after 5 seconds and only the
  node that already held the name could see it, some 30 seconds after the
  network was healed. Its leader group needed longer to re-elect than the
  workbench waits, which is where its extra disagreements come from.
* **`locker` never split-brained.** The minority side is refused with
  `no_quorum` rather than given a second owner, and all 29 lookups agreed.
  It pays with a 7 second block on a write that cannot reach a quorum, and
  by not monitoring the process: after a kill the name stays pointing at a
  dead pid until the lease expires.
* **`highlander_pg` never split-brained either, for a different reason.**
  There is only ever one advisory lock. Its 27 disagreements are the
  expected shape, not a fault: a node can only answer for itself, so a
  healthy cluster is one node saying yes and two saying nothing.
* **Losing the database does not hand the singleton over.** When n1 was cut
  off from Postgres while the BEAM cluster stayed intact, n1 kept running
  the singleton it could no longer defend, and n2's claim sat `pending` for
  the full 3 second wait and never won. Dropped packets are not a closed
  connection, so Postgres kept the session and its lock alive, and no
  failover happened for the rest of the scenario. A crashed node frees the
  lock; a partitioned one does not, until the database gives up on the
  session.

### Tuning locker

The 7 second block is the timeout on locker's `multi_call`s, and a write
that cannot reach a quorum makes two of them. It is configurable with
`LOCKER_TIMEOUT_MS`, measured on a node cut off from both peers:

| `LOCKER_TIMEOUT_MS` | Time to answer `{error, no_quorum}` |
| --- | --- |
| 5000 (locker's default) | 7003ms |
| 1000 | 2003ms |

The knob reaches `locker:lock/4` and `locker:release/3`. It does not reach
lease renewal: `locker:extend_lease/4` takes a timeout but is not exported,
so `extend_lease/3` is stuck with locker's own 5s default.

One sharp edge worth knowing: `locker:release/2` authorises on the *value*,
not on identity. Anything that can read the current value can release the
key, so ownership is the caller's job to enforce, which is what
`workbench_worker:terminate/2` does.

These are single runs, so the timings and the tie-breaks after a heal are
indicative rather than measurements. Re-run with `./run.sh` to regenerate.

## Running it

Docker is the only prerequisite. Erlang, Elixir and rebar3 are needed for
`make`, not for a run: the image builds everything, including the Elixir
registries.

```bash
./run.sh
```

That builds the image and then, for each registry in turn, starts a fresh
three node cluster plus Postgres, runs every scenario, tears the cluster
down, and finally renders the report. About 30 minutes for all seven; most
of it is waiting for the cluster to notice a broken connection.

You end up with:

| Path | What it is |
| --- | --- |
| `results/RESULTS.md` | The report, regenerated from all the data on disk |
| `results/<registry>.result` | One run's raw data, as plain Erlang terms |

One or more registries only, named as in `registry:names/0` — `global`,
`gproc`, `syn`, `horde`, `group`, `locker`, `highlander_pg`:

```bash
./run.sh horde
```

That re-runs only the registries you name and leaves the other `.result`
files alone, then re-renders the report from all of them. So adding or
re-measuring one registry costs one registry's worth of time, not a full
sweep.

Re-render the report from data already on disk, without starting a cluster:

```bash
docker compose run --rm controller report
```

The timings are configurable, which is worth doing if you are iterating:

```bash
SETTLE_MS=8000 ./run.sh global
```

See the settings table under [How it works](#how-it-works) for the rest.

## How it works

```
docker network "cluster"

  node1 ─┐
  node2 ─┼─  iptables cuts between any pair of these,
  node3 ─┘   and from any of them towards postgres

  postgres    where highlander_pg's advisory lock lives
  controller  hidden node, drives the run, never cut off
```

* **The nodes** run the registry under test plus a supervisor of trivial
  processes to register. They are the system being measured.
* **The controller** is a hidden node on the same docker network. Hidden, so
  it takes no part in the registries; on the same network, so it can still
  ask a node that has been cut off from its peers what it thinks. It drives
  the scenarios over `rpc` and writes the results.
* **Cutting the network** is `iptables -I INPUT -s <peer> -j DROP`, run
  inside a node's own container (which is why the containers get
  `NET_ADMIN`). Dropping input on one side only gives a one sided split;
  dropping on both sides gives a symmetric one. The controller has a
  different address, so a cut never affects it.
* **Postgres** is where `highlander_pg` keeps its lock. The `{cut_db, Node}`
  step cuts a node off from it while the BEAM cluster stays intact, which
  is a different failure from a netsplit and one only that registry
  notices. It is one directional, because the database container is not
  ours to run iptables in.

A few settings make the runs short enough to sit through, and are worth
knowing when reading the results:

| Setting | Value | Why |
| --- | --- | --- |
| `net_ticktime` | 5s | The default 60s means a broken connection is noticed a minute later |
| `SETTLE_MS` | 15s | How long a scenario waits after a network change |
| `ACTION_TIMEOUT_MS` | 20s | An action that takes longer is recorded as `timeout` |
| `LEASE_MS` | 60s | Long enough that leases only expire where a scenario wants them to |
| `LOCKER_TIMEOUT_MS` | 5s | locker's own default, see the tuning table above |
| `CLAIM_SETTLE_MS` | 3s | How long to wait for a registry that decides a claim asynchronously |
| `HIGHLANDER_POLLING_MS` | 300ms | How often a contender asks Postgres for the lock |

Override them per run: `SETTLE_MS=8000 ./run.sh global`.

After a heal the controller asks every node to reconnect. Distributed Erlang
only reconnects when something sends a message, and without this the results
would depend on which registry happens to poll rather than on how it
recovers.

## Reading the code

Every part is small and does one thing:

| File | What it is |
| --- | --- |
| [`src/scenario.erl`](src/scenario.erl) | The step vocabulary, and the list of scenarios |
| `src/scenario_*.erl` | One scenario each: a list of steps, no logic |
| [`src/action.erl`](src/action.erl) | The action behaviour, and the list of actions |
| `src/action_*.erl` | One action each: start, look up, stop, kill, renew |
| [`src/registry.erl`](src/registry.erl) | What a registry has to be able to do |
| `src/registry_*.erl` | One adapter per registry |
| [`src/locker_via.erl`](src/locker_via.erl) | locker behind OTP's `{via, Module, Name}` protocol |
| [`elixir/mix.exs`](elixir/mix.exs) | The Elixir side, which exists only to build the Elixir registries |
| [`src/runner.erl`](src/runner.erl) | Executes the steps and records what happened |
| [`src/netcut.erl`](src/netcut.erl) | The iptables calls |
| [`src/report.erl`](src/report.erl) | Renders the raw data into markdown |

The runner records data, the report renders it. The raw data stays in
`results/<registry>.result` as plain Erlang terms, so you can check any
number in the report against the run that produced it.

## Extending it

**A scenario**: add a module implementing the `scenario` behaviour and one
line in `scenario:all/0`. Steps are data:

```erlang
steps() ->
    [{do, n1, start_process, <<"my_scenario/service">>},
     {isolate, n3},
     settle,
     {do_all, lookup, <<"my_scenario/service">>},
     heal,
     settle,
     {do_all, lookup, <<"my_scenario/service">>}].
```

Give the scenario its own key prefix; `scenario_tests` checks that no two
scenarios share a key, so one cannot affect the next through an entry a
registry kept.

**An action**: add a module implementing the `action` behaviour and one line
in `action:all/0`. An action runs on one node and returns any printable
term.

**A registry**: add a module implementing the `registry` behaviour and one
line in `registry:adapters/0` and `registry:names/0`. An Elixir one is a
line in `elixir/mix.exs` as well. The awkward parts have
somewhere to go: `setup/1` starts the registry with the cluster already
connected, `child_specs/0` supervises anything long lived, and
`on_cluster_ready/1` runs once all nodes are up, for registries that need to
be told the membership. `settings/0` puts whatever a reader needs to
interpret the numbers into the report.

## Development

```bash
make            # everything CI runs
make test       # eunit
make type_check # eqwalizer, via elp
make dialyzer
```

Type checking uses [ELP](https://github.com/WhatsApp/erlang-language-platform);
install the binary for your OTP version from its releases page. None of
these targets need Elixir: the Elixir registries are built inside the
image, and the modules that call them are excluded from xref and dialyzer
because no Erlang tool can see them from here. The tests
cover the parts that do not need a cluster: the report renderer, the step
vocabulary, and that every registry and action is wired up.

## Not included, but worth adding

The gap in the current set is a CRDT based registry and a Raft based one:

| Candidate | Why it would add something |
| --- | --- |
| [Swarm](https://github.com/bitwalker/swarm) | Distributed registry with name handoff and conflict resolution after a netsplit heals |
| [khepri](https://github.com/rabbitmq/khepri) or [ra](https://github.com/rabbitmq/ra) | A real Raft store, so a CP comparison against locker's quorum writes |
| `pg` (OTP kernel) | Process groups rather than unique names, so a different shape, but it is what pg2 became and what syn uses internally |
| A blocking `pg_advisory_lock` | The hand rolled version of what highlander_pg does, to see what its polling costs |

Swarm is Elixir, which is no longer an obstacle: the image already carries
Elixir for highlander_pg and horde, so it is a `mix.exs` line and an
adapter.

## Caveats

* Three nodes only. A cut is between node containers, so the shape of a
  partition is limited to what three nodes can express.
* The `do_all` steps ask the nodes one after another, milliseconds apart,
  not simultaneously. A registry that converges within those milliseconds
  can look more consistent than it is.
* `kernel`'s `prevent_overlapping_partitions` is left at its default, which
  is `true` since OTP 25. It makes `global` actively disconnect nodes to
  avoid overlapping partitions, and that affects every node in the cluster,
  not only `global`. The value used is recorded in the report.
* Results are one run each, not a distribution. Timings in particular will
  differ on your machine.
* `highlander_pg` is measured through the same actions as the others, but
  it answers a different question: it runs a singleton, it does not tell
  the cluster where that singleton is. Read its owner counts, not its
  agreement counts.
